# 03 — ESP32 Firmware Specification (ESP32-PICO-MINI-02)

## 1. Platform

| Item | Value |
|---|---|
| Module | ESP32-PICO-MINI-02 — dual LX6 240 MHz, 8 MB flash, 2 MB PSRAM, BT Classic + BLE + Wi-Fi |
| SDK | ESP-IDF pinned to the version BlueRetro requires (submodule) |
| Language | C++17 for project code; BlueRetro's Bluetooth host stays in C as its own component; pico_usb ported as a component |
| Build | `idf.py build flash monitor` |

The classic ESP32 is required for BR/EDR (BlueRetro: Wii, PS3/4, Switch…). It has no native USB — all USB goes through the FPGA.

**The ESP32 is not on the cold-boot path.** The FPGA boots from its NOR and serves the boot bank on its own (00-system §4). The ESP32 attaches when ready and must cope with finding the console already running, mid-boot, or off.

## 2. Software architecture

```
            core 0                                     core 1
 ┌──────────────────────────┐      ┌──────────────────────────────────────────────────┐
 │ BT controller + host     │      │ fpga_svc   (high)  IRQ_N → dispatch              │
 │ BlueRetro bt_host        │      │ usb_task   (high)  pico_usb usbd + FPGA DCD      │
 │ BlueRetro adapter mapping│──┐   │ legacy     (mid)   iotrap event decode →         │
 └──────────────────────────┘  │   │                    personalities → renderers     │
     GamepadIn / GamepadOut    └──►│ rom_mgr    (mid)   catalogue, NOR writes, select │
     (lock-free, per slot)         │ msc        (mid)   SCSI/BOT ↔ sdspi raw blocks   │
                                   │ led_task   (low)   RMT NeoPixels                 │
                                   │ lcd_task   (low)   SPI LCD (shares SD bus)       │
                                   │ host_link  (low)   PC protocol on UART0          │
                                   └──────────────────────────────────────────────────┘
       drivers: fpga_link (VSPI, dedicated), periph_bus (HSPI: SD card + LCD),
                cfg_bus (HSPI re-pinned onto the config bus for NOR / slave config — recovery only),
                smbus (I2C0 master; I2C1 slave later)
```

**Threading**: plain ESP-IDF FreeRTOS tasks on both cores. BlueRetro's bare-metal core-1 machinery (high-level interrupts, timing-critical wired-output ISRs) exists to bit-bang console controller protocols and is not used: every hard-timed interface is in the FPGA. Code that must run while the ESP32's own flash is being written (NVS, OTA) — in practice only small ISRs such as `FPGA_IRQ_N`, which just notify a task — is placed in IRAM; everything else runs from flash.

## 3. Startup

1. Boot (not boot-critical, but aim for < 300 ms to `app_main`; quiet logs).
2. `FPGA_CDONE` high? → open link, read `ID`/`VERSION`/`BOOT_STATUS`. Low after 500 ms → recovery: check NOR (JEDEC ID, bitstream header) via `cfg_bus`; if blank/corrupt, write the golden bitstream from ESP32 flash, reset FPGA. (This is also the factory-programming path.)
3. Version mismatch → leave LPC registers alone (FPGA is already serving from boot config), signal "update needed", offer `oxctl fpga update`.
4. Read live state (`LPC_STATUS`, `ACTIVE_BANK`, reset count) — console may already be running. Don't disturb serving.
5. Drain the iotrap event FIFO (traffic from before we booted) into the personality layer.
6. Init `periph_bus` (SD card probe, LCD). Start USB (`PULLUP` on), BT, LEDs, LCD.

## 4. ESP32 flash layout (8 MB)

| Name | Type | Offset | Size | Contents |
|---|---|---|---|---|
| `nvs` | data/nvs | 0x009000 | 24 KB | ESP32-local settings, BT bonds if not in `storage` |
| `otadata` | data/ota | 0x00F000 | 8 KB | |
| `phy_init` | data/phy | 0x011000 | 4 KB | |
| `ota_0` | app | 0x020000 | 3 MB | Firmware |
| `ota_1` | app | 0x320000 | 3 MB | Firmware |
| `golden` | data/0x40 | 0x620000 | 256 KB | Golden FPGA bitstream + golden boot config (recovery/factory) |
| `storage` | data/spiffs | 0x660000 | 1.5 MB | BlueRetro config/pairings; spare |

ROMs no longer live here — they're in the FPGA's NOR (01-interface §6.1), managed over the link. The ESP32 owns the catalogue format (NOR 0x042000).

## 5. ROM management (`rom_mgr`)

- **Catalogue** (NOR, ESP32-owned, A/B copies with sequence + CRC): per slot-run `{name[32], role (Loader A/B, System A/B, Diag, User), size_code, first_slot, crc32, sha256, flags: PROTECTED, CONSOLE_MODIFIED, MIRROR_REDUCED, FAILED_BOOT}`. Roles, boot decisions and updates: 06-boot-flow.
- **Adding a ROM**, by source:

  | Source | Path | Phase |
  |---|---|---|
  | PC (`oxctl`) over UART0 | ESP32 → link NOR program (console on) or `cfg_bus` (console off, faster) | 1 |
  | Console software (System UI, or any app using `libs/oxprog`) via the mailbox | programmer protocol (07-console-protocol) → ESP32 → NOR | 1 |
  | Any existing Xbox flasher | `flash_emu` writes the active bank directly; ESP32 gets `FLASHEMU` and re-catalogues (CRC, mark `CONSOLE_MODIFIED`) | 3 |

  On import: size check (256/512/1024 K), mirror-reduce (a 512 K/1 M image that repeats its first 256 K is stored as 256 K), CRC verify with the FPGA CRC engine, then commit the catalogue entry.
- **Selection** → `rom_select(id, when)`, `when` ∈ {`AT_RESET`, `NOW`, `BOOT_DEFAULT`}:
  - `AT_RESET`: `PENDING_BANK` + `ARM_AT_RESET`; on `BANK_SWAPPED` update state/LED.
  - `NOW`: only while console off / in reset, else requires `--force` (uses `PAUSE`).
  - `BOOT_DEFAULT`: rewrite the boot config record (alternate slot, sequence+1) — this is what the console boots next cold start, ESP32 or not.
  - Inputs: `oxctl`, gamepad hotkey (e.g. hold Back+Start+Black 3 s → cycle; LED/LCD shows the choice), mailbox, legacy bank-select (handled in FPGA, reflected here), LCD menu.
- **Write safety**: never erase the slot currently being served while `LRESET#` is high unless forced; protected slots enforced by `PROTECT_MASK` (FPGA) and by `rom_mgr`.

## 6. Legacy personality layer (`legacy/`)

```
 iotrap events ──► personality (e.g. xenium.cpp) ──► abstract outputs ──► renderers
 (port,data,Δt)    decodes protocol: HD44780         Lcd: text grid,       SPI LCD (lvgl),
                   cmds, bit-banged SPI, LED regs    cursor, backlight     HD44780 on I2C backpack,
                   updates shadow RAM for reads      Led: RGB/state        NeoPixel strips
                                                     Bank: select          rom_mgr
```

- A personality = a table of iotrap windows (modes, shadow init values, bank map) + a decoder. Enabled set chosen in config; its windows are also written into the **boot config record** so they're active from cold boot (writes are queued in the FPGA, reads served from shadow) before the ESP32 runs.
- First personality: Xenium (LED at `0xEE`; bank select, bit-banged LCD and status at `0xEF`; observed behaviour in 02-fpga §6.2). Then SmartXX, Xecuter 3 and Aladdin LCD ports.
- Renderers are independent of personalities: e.g. a SmartXX HD44780 stream renders to the SPI LCD as a 20×4 text grid; a Xenium LED register renders to NeoPixels.

## 7. FPGA drivers

### 7.1 `cfg_bus` (HSPI via GPIO matrix, borrowed from `periph_bus`)
- The ESP32 has only two general-purpose SPI hosts (VSPI = link, HSPI = SD/LCD). Config-bus access is rare, so `cfg_bus` asks `periph_bus` to quiesce (MSC reports "not ready", LCD paused), frees the HSPI bus, re-initialises it on the config-bus pins, and reverses that on `release()`. SD/LCD pins and config-bus pins are separate wires — they can't be shared because the running FPGA drives the config bus.
- `hold_fpga(true)` → `CRESET_N` low, then drive bus. `nor_*` primitives (ID, read, erase, program, status, power-down/up). `slave_config(bitstream)`. `release()` → pins Hi-Z, `CRESET_N` high, wait `CDONE`.
- Used for: factory programming, recovery, bitstream update (write `0x000000` region from a verified image; keep golden in ESP32 flash), bulk ROM writes while the console is off.
- **Never** called while `LRESET#` is high without user confirmation — holding the FPGA in reset takes the BIOS off the bus.

### 7.2 `fpga_link` (VSPI, GPIO matrix)
- Polling transactions for registers (~10 µs), DMA for bulk. One mutex; the bus is dedicated to the FPGA so USB servicing never waits behind an LCD frame or SD transfer.
- API: `reg_*`, `nor_read`, `nor_program/erase` (via program buffer + `NOR_OP`), `crc`, `fifo_*`, `slot_buf_*`.

### 7.3 `periph_bus` (HSPI)
- SD card via ESP-IDF `sdspi` host (400 kHz init, then 20 MHz; ~2 MB/s raw) and the LCD as a second `spi_device`, both arbitrated by the IDF bus lock. There is no card-detect pin: with no card present the card is probed about once a second; removal shows up as failed commands.
- SD in SPI mode on a shared bus: SD gets its CS high + ≥ 8 idle clocks before LCD traffic (cards may hold MISO otherwise); give the SD card the higher priority — MSC throughput beats LCD frame rate. Every call latches STS/error bits.

### 7.4 `fpga_svc`
`IRQ_N` ISR → notify. Task reads `IRQ_STATUS` (+USB bitmaps) in one burst and dispatches: USB → DCD; `LRST_*`/`BANK_SWAPPED` → rom_mgr/LEDs; `IOTRAP` → legacy; `MBX_RX` → mailbox; `FLASHEMU` → flash_emu_svc; `NOR_DONE`/`CRC_DONE` → waiters; `ERROR` → log.

## 8. USB device stack

- **pico_usb**: `usbd.c` core with pluggable `dcd_driver_t`. Supports multiple devices (`USBD_DEVICES_MAX`) for hub emulation — hub first, then downstream devices — and per-device class drivers.
- **`dcd_openox_fpga`** implements `dcd_driver_t` against 01-interface §5.9: `init/connect` (SIE_EN, PULLUP), `set_address(dport, addr)` (`DEV_ADDR` with `DEFER`), `ep_open/close` (allocate/free a slot: `SLOT_CFG/SLOT_EP`), `ep_read_setup` (SPACE 1 `0x800 + 8·dport`), `ep_read/ep_write` (slot buffers, `SLOT_LEN/SLOT_CMD`), `ep_set_stall/stalled/ready`, `get_frame`, `task` (returns event/ep masks from the IRQ snapshot), plus the "answers at address 0" control for the device the hub is currently resetting.
- **Functions**: port ox's `xid.cpp` (XID 0x58/0x42, XID descriptor, capability reports, 20 B in / 6 B rumble out), `msc.cpp` (backed by `msc_sd`), optional `cdc.cpp` (debug).
- **Profiles** (selectable, decided by the Q2 experiment):

  | Profile | Topology | Notes |
  |---|---|---|
  | `single` | 1 device, 1 XID | Bring-up baseline |
  | `composite` | 1 device: up to 4 XID interfaces + MSC | ox's default (`gamepad;gamepad;gamepad;gamepad;msc`) |
  | `duke` | hub + XID + MSC (as a memory unit) | Looks like a real controller with an MU inserted |
  | `hub4` | hub + up to 3 downstream XID/MSC | Multi-player via hub — depends on kernel port mapping |

- Latency: link round trip ~20–40 µs per packet vs. 1–8 ms interrupt intervals — comfortable. MSC ~0.8–1 MB/s (USB FS bulk is the ceiling; SD and link both have headroom).

## 9. SD card as USB mass storage (`msc_sd`)

- The card is on `periph_bus`. The ESP32 never mounts it while it is presented over USB. It implements SCSI (INQUIRY, READ CAPACITY, READ(10)/WRITE(10), TEST UNIT READY, REQUEST SENSE, MODE SENSE, PREVENT/ALLOW) for the MSC function on top of `sdmmc_read_sectors`/`sdmmc_write_sectors`, double-buffering 512 B sectors against 64 B bulk packets.
- Card found by polling → media change (UNIT ATTENTION); card lost → NOT READY.
- Optional later: with the MSC function detached (or the console off, with standby), the ESP32 may mount the card's FAT to import ROMs into the NOR. One owner at a time, enforced in `msc_sd`.
- Use case: the Xbox reads ROMs (and anything else) from the card and uploads them to the chip via the mailbox app or a flasher. What filesystem the Xbox can read (FAT vs. FATX, MU size limits) depends on the kernel/dashboard (00-system Q2).

## 10. Bluetooth gamepads (BlueRetro)

- BlueRetro as a component with output system `CONFIG_BLUERETRO_SYSTEM_OPENOX`.
- Reuse `main/adapter/wired/xadapter.cpp` (BlueRetro → `GamepadIn`, `GamepadOut` → rumble); replace `wired/xadapter_spi.cpp` (SPI-slave transport to the RP2350) with an in-process lock-free per-slot buffer read by the XID function. The 32-byte `SpiProtocol` frame format is dropped.
- Disable BlueRetro's wired-timing machinery (high-level interrupts, core-1 ISRs) for this system.
- Without standby, controllers reconnect each console power-on (~1–3 s). With standby (optional), they stay connected and can wake the console (needs the power-button wire).
- `oxctl bt list | pair | forget`.

## 11. NeoPixels, LCD

- **NeoPixels**: 2 RMT channels, WS2812/SK6812, length/brightness/current-limit in NVS. Status overlay priority: NOR write/flash-emu > error > console off > no LCLK > serving > idle; plus legacy LED renderer and per-player colours.
- **LCD**: SPI (ST7789/ILI9341 class) on `periph_bus` (shared with the SD card) with its own CS + DC + backlight PWM; LVGL. Shows console state, active ROM, controllers, COM activity; renders legacy LCD text; ROM picker driven by gamepad.

## 12. PC protocol (`host_link`)

UART0 through bridge channel A, 921600 baud 8N1 (higher if the bridge allows). Binary only; `tools/oxctl.py` is the human interface.

- **Framing**: COBS, frames delimited by `0x00`. Frame = `type (1) | seq (1) | len (2, LE) | payload | CRC-32 (4, LE)` before encoding. Anything that fails the CRC is dropped, so boot-ROM text before the app starts is ignored.
- **Flow**: the PC sends requests; every request gets exactly one response with the same `seq` (`OK` + payload, or `ERR` + code). The ESP32 sends unsolicited `EVENT` frames (console reset, bank swapped, SMBus alert…).
- **Logs**: once the app runs, ESP-IDF logging is redirected into `LOG` frames; nothing else is written to UART0.
- **Bulk data** (ROM images, bitstreams, firmware): `begin(target, size, crc32)`, then `data(offset, ≤ 4 KB)` chunks each acknowledged, then `end`, which verifies the whole image with the FPGA CRC engine (or the ESP32's for its own firmware) before committing.

| Group | Commands |
|---|---|
| `sys` | version, status, reboot, ESP32 firmware update |
| `rom` | list, info, upload, delete, protect, select (`now` / `at_reset` / `default`) |
| `fpga` | info, bitstream update, recover, reset, boot config read/write |
| `nor` | the FPGA's flash through its NOR engine while it serves: info, read, erase, program, CRC |
| `lpc` | serve on/off, D0 / LFRAME# mode, COM baud/route |
| `smbus` | raw read/write byte/word/block; named actions: reset, power cycle, power off, temperatures, tray/boot reason |
| `log` | level per tag |
| `prog` | one programmer protocol packet in, its reply out (07-console-protocol): the PC gets everything the console does |
| `usb`, `bt`, `led`, `legacy` | (later phases) |

## 13. SMBus (`smbus`)

The Xbox SMBus (LPC header pins 13/14, 3.3 V) is wired to the ESP32, not the FPGA: it is slow and protocol-level, with no hard timing.

- **Master** (I2C0, 100 kHz): reads the SMC (0x10) for tray state, fan and boot reason; the temperature sensor (0x4C) for CPU/board temperatures; the EEPROM (0x54) read-only. Writes SMC commands for reset, power cycle and power off, so `oxctl` plus the kernel debugger on COM make a complete remote debugging setup. The MCPX is the other master: transactions are short, lost arbitration is detected by the I2C hardware and retried.
- **Power on** is not possible over SMBus without standby power (the ESP32 is off with the console); it needs the optional standby supply and power-button wire.
- **Slave** (I2C1 on the same pins, later): an unused address exposing small data tables to Xbox-side software. Optional.

## 14. First firmware scope

1. `fpga_link`, `fpga_svc` (status, IRQ).
2. `cfg_bus`: program and verify the FPGA's NOR; recovery.
3. `host_link` + `oxctl`.
4. `rom_mgr`: upload, catalogue, selection, boot config.
5. `smbus` master.

USB, Bluetooth, legacy personalities, SD and LCD follow.
