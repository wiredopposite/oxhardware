# 03 — ESP32 Firmware Specification (ESP32-PICO-MINI-02)

## 1. Platform

| Item | Value |
|---|---|
| Module | ESP32-PICO-MINI-02 — dual LX6 240 MHz, 8 MB flash, 2 MB PSRAM, BT Classic + BLE + Wi-Fi |
| SDK | ESP-IDF pinned to the version BlueRetro requires (submodule) |
| Language | C++17 for project code; BlueRetro's Bluetooth host stays in C as its own component; pico_usb ported as a component |
| Build | `idf.py build flash monitor` |

The classic ESP32 is required for BR/EDR (BlueRetro: Wii, PS3/4, Switch…). It has no native USB — all USB goes through the FPGA.

**The ESP32 is not on the cold-boot path.** The FPGA boots from its NOR and serves the boot bank on its own (00-system §4). The ESP32 attaches when ready and must cope with finding the console already running, mid-boot, or off.

## 2. Software architecture

```
            core 0                                     core 1
 ┌──────────────────────────┐      ┌──────────────────────────────────────────────────┐
 │ BT controller + host     │      │ fpga_svc   (high)  IRQ_N → dispatch              │
 │ BlueRetro bt_host        │      │ usb_task   (high)  pico_usb usbd + FPGA DCD      │
 │ BlueRetro adapter mapping│──┐   │ legacy     (mid)   iotrap event decode →         │
 └──────────────────────────┘  │   │                    personalities → renderers     │
     GamepadIn / GamepadOut    └──►│ rom_mgr    (mid)   catalogue, NOR writes, select │
     (lock-free, per slot)         │ msc        (mid)   SCSI/BOT ↔ sdspi raw blocks   │
                                   │ led_task   (low)   RMT NeoPixels                 │
                                   │ lcd_task   (low)   SPI LCD (shares SD bus)       │
                                   │ host_link  (low)   PC protocol on UART0          │
                                   └──────────────────────────────────────────────────┘
       drivers: fpga_link (VSPI, dedicated), periph_bus (HSPI: SD card + LCD),
                cfg_bus (HSPI re-pinned onto the config bus: every NOR access, slave config),
                smbus (I2C0 master; I2C1 slave later)
```

**Threading**: plain ESP-IDF FreeRTOS tasks on both cores. BlueRetro's bare-metal core-1 machinery (high-level interrupts, timing-critical wired-output ISRs) exists to bit-bang console controller protocols and is not used: every hard-timed interface is in the FPGA. Code that must run while the ESP32's own flash is being written (NVS, OTA) — in practice only small ISRs such as `FPGA_IRQ_N`, which just notify a task — is placed in IRAM; everything else runs from flash.

## 3. Startup

1. Boot (not boot-critical, but aim for < 300 ms to `app_main`; quiet logs).
2. `FPGA_CDONE` high? → open link, read `ID`/`VERSION`/`BOOT_STATUS`. Low after 500 ms → recovery: check NOR (JEDEC ID, bitstream header) via `cfg_bus`; if blank/corrupt, write the golden bitstream from ESP32 flash, reset FPGA. (This is also the factory-programming path.)
3. Version mismatch → leave LPC registers alone (FPGA is already serving from boot config), signal "update needed", offer `oxctl fpga update`.
4. Read live state (`LPC_STATUS`, `ACTIVE_BANK`, reset count) — console may already be running. Don't disturb serving.
5. Drain the iotrap event FIFO (traffic from before we booted) into the personality layer.
6. Init `periph_bus` (SD card probe, LCD). Start USB (`PULLUP` on), BT, LEDs, LCD.

## 5. ROM management (`rom_mgr`)

- **Catalogue**: two 4 KB copies, A at `0x042000` and B at `0x043000` (`0x022000` / `0x023000` on parts up to 4 MB, chosen from the JEDEC size). Each write goes to the other copy with the sequence number + 1 and is verified by CRC; the newest valid copy wins, and a copy that can't be read is never treated as empty. All fields little-endian, packed:

  | Offset | Size | Field |
  |---|---|---|
  | 0 | 4 | Magic `'X','O','R','C'` (`0x43524F58`) |
  | 4 | 2 | Version (1) |
  | 6 | 2 | Entry size (52) |
  | 8 | 4 | Sequence (wrapping) |
  | 12 | 1 | Entry count (64) |
  | 13 | 3 | Reserved |
  | 16 | 52 × 64 | Entries |
  | 3344 | 4 | CRC-32 of everything before it |

  Entry: role (1, 07-console-protocol `Role`), bank (1, `ACTIVE_BANK` format, `0xFF` = unused), flags (1, `RomFlags`), reserved (1), size (4), CRC-32 (4), source CRC-32 (4), version (2), reserved (2), name (32, NUL-padded). An entry's ID is its index, so IDs don't change when others are deleted. Roles, boot decisions and updates: 06-boot-flow.
- **Allocation**: an upload takes a free run of slots aligned to its size (256 K, 512 K or 1 M; Loader and Diag 256 K). Slots in the catalogue, `ACTIVE_BANK`, `DEFAULT_BANK` and an armed `PENDING_BANK` are never used. Of the free runs it picks the one whose enclosing 512 K and 1 M blocks are most used (slots past the end of flash count as used), so small images pack together and 1 M runs stay open.
- **Compaction**: when no aligned run is free but moving entries would make one, Begin returns `Fragmented` instead of `NoSpace`. `Compact` then empties the aligned run that needs the fewest slots moved, one entry per request, largest first. Entries in pinned slots (active, default, armed) are never moved. Each move copies the entry to its new slots, checks the CRC, then saves the catalogue. A power loss before the save leaves the old entry in use. Each 64 KB block is erased the first time the upload writes to it; the commit checks the CRC of the whole range before the entry is written.
- **Trials**: a Loader or System committed with `Trial` gets the catalogue flag `trial` instead of becoming current, and is armed with `TRIAL_PENDING`. A watcher task follows it through 06-boot-flow §7: on confirmation the entry becomes current and the old one the spare; on a failure it is flagged `failed-boot`.
- **Failed boots**: the same task judges every other armed boot by 06-boot-flow §6, reading `LPC_RESET_COUNT`, `LPC_STATUS`, `BOOT_FLAGS` and `MEM_READ_COUNT`. The LRESET# interrupts wake it; it polls every 50 ms while a boot is being timed. A single low CDONE read only skips a pass, since the line can glitch during heavy LPC traffic. A failure sets `LAST_FAILED` and flags the entry `failed-boot`, and resets the console if the SMC isn't already doing so.
- **Bank registers**: after every catalogue change the ESP32 sets `USER_BANK`, `SYSTEM_BANK` and `DIAG_BANK` from it, and `DEFAULT_BANK` when there is a current Loader.
- **Adding a ROM**, by source:

  | Source | Path | Phase |
  |---|---|---|
  | PC (`oxctl`) over UART0 | ESP32 → `nor` (flash borrowed from the FPGA) | 1 |
  | Console software (System UI, or any app using `libs/oxprog`) via the mailbox | programmer protocol (07-console-protocol) → ESP32 → NOR | 1 |
  | Any existing Xbox flasher | `flash_emu` writes the active bank directly; ESP32 gets `FLASHEMU` and re-catalogues (CRC, mark `CONSOLE_MODIFIED`) | 3 |

  On import: size check (256/512/1024 K), CRC verify, mirror-reduce, then commit the catalogue entry. Mirror-reduce compares the CRCs of the image's 256 K (then 512 K) pieces; an image that repeats its first 256 K or 512 K is stored as that, and its other slots are free again. The console reads the same bytes, since the bank mirrors through the 1 MB window. The entry's size and CRC are those of the stored image, so a download returns the reduced image.
- **Selection** → `rom_select(id, when)`, `when` ∈ {`AT_RESET`, `NOW`, `BOOT_DEFAULT`}:
  - `AT_RESET`: `PENDING_BANK` + `ARM_AT_RESET`; on `BANK_SWAPPED` update state/LED.
  - `NOW`: only while console off / in reset, else requires `--force` (uses `PAUSE`).
  - `BOOT_DEFAULT`: rewrite the boot config record (alternate slot, sequence+1) — this is what the console boots next cold start, ESP32 or not.
  - Inputs: `oxctl`, gamepad hotkey (e.g. hold Back+Start+Black 3 s → cycle; LED/LCD shows the choice), mailbox, legacy bank-select (handled in FPGA, reflected here), LCD menu.
- **Write safety**: never erase the slot currently being served while `LRESET#` is high unless forced; protected slots enforced by `PROTECT_MASK` (FPGA) and by `rom_mgr`.

## 6. Legacy personality layer (`legacy/`)

```
 iotrap events ──► personality (e.g. xenium.cpp) ──► abstract outputs ──► renderers
 (port,data,Δt)    decodes protocol: HD44780         Lcd: text grid,       SPI LCD (lvgl),
                   cmds, bit-banged SPI, LED regs    cursor, backlight     HD44780 on I2C backpack,
                   updates shadow RAM for reads      Led: RGB/state        NeoPixel strips
                                                     Bank: select          rom_mgr
```

- A personality = a table of iotrap windows (modes, shadow init values, bank map) + a decoder. Enabled set chosen in config; its windows are also written into the **boot config record** so they're active from cold boot (writes are queued in the FPGA, reads served from shadow) before the ESP32 runs.
- First personality: Xenium (LED at `0xEE`; bank select, bit-banged LCD and status at `0xEF`; observed behaviour in 02-fpga §6.2). Then SmartXX, Xecuter 3 and Aladdin LCD ports.
- Renderers are independent of personalities: e.g. a SmartXX HD44780 stream renders to the SPI LCD as a 20×4 text grid; a Xenium LED register renders to NeoPixels.

## 7. FPGA drivers

### 7.1 `cfg_bus` (HSPI via GPIO matrix, borrowed from `periph_bus`)
- The ESP32 has only two general-purpose SPI hosts (VSPI = link, HSPI = SD/LCD). Config-bus access comes in short bursts (one per NOR operation), so `cfg_bus` asks `periph_bus` to quiesce (MSC reports "not ready", LCD paused), frees the HSPI bus, re-initialises it on the config-bus pins, and reverses that on `release()`. SD/LCD pins and config-bus pins are separate wires — they can't be shared because the running FPGA drives the config bus.
- `hold_fpga(true)` → `CRESET_N` low, then drive bus. `nor_*` primitives (ID, read, erase, program, status, power-down/up). `slave_config(bitstream)`. `release()` → pins Hi-Z, `CRESET_N` high, wait `CDONE`.
- Held: factory programming, recovery, bitstream update (write `0x000000` region from a verified image; keep golden in ESP32 flash).
- Taken (`Take()`/`Give()`): the same flash primitives with the FPGA running, once `nor` has been granted the flash (01-interface §5.5). `nor` wraps each operation: request, wait for `GRANT` (up to 3 s), take the bus, operate, wait until the flash is idle, give the bus back, clear the request, log `FLASH_MISS` if the console read meanwhile. Erases and programs below the catalogue are refused unless held.
- **Never** called while `LRESET#` is high without user confirmation — holding the FPGA in reset takes the BIOS off the bus.

### 7.2 `fpga_link` (VSPI, GPIO matrix)
- Polling transactions for registers (~10 µs), DMA for bulk. One mutex; the bus is dedicated to the FPGA so USB servicing never waits behind an LCD frame or SD transfer.
- API: `reg_*`, `fifo_*`, `slot_buf_*`. The flash is not reached through the link: `nor` borrows it and drives the config bus (`cfg_bus`).

### 7.3 `periph_bus` (HSPI)
- SD card via ESP-IDF `sdspi` host (400 kHz init, then 20 MHz; ~2 MB/s raw) and the LCD as a second `spi_device`, both arbitrated by the IDF bus lock. There is no card-detect pin: with no card present the card is probed about once a second; removal shows up as failed commands.
- SD in SPI mode on a shared bus: SD gets its CS high + ≥ 8 idle clocks before LCD traffic (cards may hold MISO otherwise); give the SD card the higher priority — MSC throughput beats LCD frame rate. Every call latches STS/error bits.

### 7.4 `fpga_svc`
`IRQ_N` ISR → notify. Task reads `IRQ_STATUS` (+USB bitmaps) in one burst and dispatches: USB → DCD; `LRST_*`/`BANK_SWAPPED` → rom_mgr/LEDs; `IOTRAP` → legacy; `MBX_RX` → mailbox; `FLASHEMU` → flash_emu_svc; `ERROR` → log.

- Tasks register the bits they want with `FpgaSvc::Notify(mask, task)` and get a task notification when any of them is raised. The bits only say that something happened; the task then reads the state it needs. `IRQ_ENABLE` is the union of the registered masks.
- `IRQ_STATUS` and `IRQ_ENABLE` are read in one 4-byte burst, and the pending bits are cleared before anyone is notified, so an event after that raises the line again and is never lost.
- The pin interrupt is level-triggered and masks itself; the task unmasks it after each pass. If the line is low with nothing enabled pending (FPGA not configured, pin not driven), it stays masked for 100 ms.
- The task also runs every 100 ms without an interrupt and rewrites `IRQ_ENABLE` if the FPGA has lost it (reconfigured).
- Users: mailbox (`MBX_RX`), rom_mgr's watcher (`LRST_ASSERT`, `LRST_DEASSERT`, `BOOTCTL`). Each keeps a slow poll (100 ms / 1 s) as a fallback.
- `oxctl link irq` (command `0x0304`) shows interrupts taken, spurious wakeups and counts per bit.

## 8. USB device stack

- **pico_usb**: `usbd.c` core with pluggable `dcd_driver_t`. Supports multiple devices (`USBD_DEVICES_MAX`) for hub emulation — hub first, then downstream devices — and per-device class drivers.
- **`dcd_fpga`** implements `dcd_driver_t` against 01-interface §5.9. The FPGA does every handshake from slot state; the driver fills IN slots, empties OUT slots and keeps the address and endpoint maps.
  - `init` clears the endpoint map and the event registers and enables the SIE; `connect` turns the pull-up on; `deinit` turns both off (the host sees a detach).
  - Device *d*'s EP0 is IN slot *d* and OUT slot 16 + *d*; slots 0–7 and 16–23 are the FPGA's EP0 slots however many devices usbd runs (`USBD_DEVICES_MAX` = 4: hub, pad, two memory units). `ep_open` gives other endpoints a free slot from 8–15 or 24–31 and an endpoint map entry.
  - `ep_write` copies into the IN slot and arms it (two link writes); `ep_read` reads the length and data, then frees the slot.
  - Addresses: after a bus reset, device 0 (the hub, or the only device) answers at 0. `set_address(d, 0)` from a hub port reset moves address 0 to device *d*. Reading a SET_ADDRESS SETUP arms the FPGA's deferred SET_ADDRESS, so the new address is mapped exactly when the host acknowledges the status stage; the old one is unmapped afterwards.
  - `dcd_fpga_poll()` reads `USB_IRQ` through `USB_OUT_DONE` in one burst, clears exactly the bits it read and queues events per device. An EP0 completion read together with a new SETUP for the same device belongs to the previous transfer (the SETUP reset both EP0 slots): it goes to usbd first, without touching the hardware, and the SETUP on the next pass. A non-empty EP0 OUT read with a SETUP is its data stage and goes after it. Only devices usbd runs count as pending: a bus reset is queued for all eight.
- **`usb_dev`**: one task (priority 9) woken by `IRQ_STATUS.USB`, and every 2 ms for the functions' timed work. Each pass polls the driver and runs `usbd_task()` until nothing is pending. `oxctl usb start|stop|status` (commands `0x0700`–`0x0702`); `start` refuses unless the FPGA's `FEATURES` has USB.
- **Bring-up profiles** (`oxctl usb start pad|hub`):
  - `HidTest`: one HID gamepad (pid.codes test VID/PID 1209:0001) that toggles button 1 every second.
  - `HubTest`: a 4-port full-speed hub (1209:0002) as device 0, with the test gamepad on port 1. `oxctl usb unplug|plug` takes the gamepad off port 1 and puts it back (command `0x0703`).
  - `Xbox`: a controller as the console sees one: a 3-port hub (1209:0002, 8-byte EP0) with an XID gamepad (1209:0003) on port 1; ports 2 and 3 are for memory units. `oxctl usb pad <buttons> [--lx/--ly/--rx/--ry N]` sets the pad's state (command `0x0704`, answers with the last rumble).
  - `HidTest` and `HubTest` enumerate on a PC with `lpc_com`.
- **XID gamepad** (`xid_pad.c`): interface class 0x58/0x42, interrupt IN and OUT, 32 bytes, interval 4. Answers the XID descriptor (vendor GET_DESCRIPTOR, type 0x42; type gamepad, subtype controller S), GET_CAPABILITIES (vendor request 1: all report bits implemented), GET_REPORT (the 20-byte input report) and SET_REPORT or OUT reports (6-byte rumble). An input report goes out when the state changes.
- **Hub** (`hub.c`): per-port power switching, all ports removable. Port state follows the host's SET/CLEAR_FEATURE. A port reset resets the device behind it at once (it then answers at address 0) and reports `C_PORT_RESET`. Changes go out on the 1-byte status change endpoint (interval 12 ms). A port shows a connection only while it is powered and has a device attached, and only 100 ms after the port was powered or the device attached (power good is 50 ms), as on a real hub: reported at once, the console's hub driver can take the change while it is still powering the other ports and then never asks about that port. Devices attach and detach at any time: detaching reports `C_PORT_CONNECTION` and takes the device off the bus at once (`dcd_fpga_detach`: its address is unmapped and its endpoints closed), and it answers again only after the host resets its port.
- **Functions**: port ox's `xid.cpp` (XID 0x58/0x42, XID descriptor, capability reports, 20 B in / 6 B rumble out), `msc.cpp` (backed by `msc_sd`), optional `cdc.cpp` (debug).
- **Profiles** (selectable, decided by the Q2 experiment):

  | Profile | Topology | Notes |
  |---|---|---|
  | `single` | 1 device, 1 XID | Bring-up baseline |
  | `composite` | 1 device: up to 4 XID interfaces + MSC | ox's default (`gamepad;gamepad;gamepad;gamepad;msc`) |
  | `duke` | hub + XID + MSC (as a memory unit) | Looks like a real controller with an MU inserted |
  | `hub4` | hub + up to 3 downstream XID/MSC | Multi-player via hub — depends on kernel port mapping |

- Latency: link round trip ~20–40 µs per packet vs. 1–8 ms interrupt intervals — comfortable. MSC ~0.8–1 MB/s (USB FS bulk is the ceiling; SD and link both have headroom).

## 9. SD card as USB mass storage (`msc_sd`)

- The card is on `periph_bus`. The ESP32 never mounts it while it is presented over USB. It implements SCSI (INQUIRY, READ CAPACITY, READ(10)/WRITE(10), TEST UNIT READY, REQUEST SENSE, MODE SENSE, PREVENT/ALLOW) for the MSC function on top of `sdmmc_read_sectors`/`sdmmc_write_sectors`, double-buffering 512 B sectors against 64 B bulk packets.
- Card found by polling → media change (UNIT ATTENTION); card lost → NOT READY.
- Optional later: with the MSC function detached (or the console off, with standby), the ESP32 may mount the card's FAT to import ROMs into the NOR. One owner at a time, enforced in `msc_sd`.
- Use case: the Xbox reads ROMs (and anything else) from the card and uploads them to the chip via the mailbox app or a flasher. What filesystem the Xbox can read (FAT vs. FATX, MU size limits) depends on the kernel/dashboard (00-system Q2).

## 10. Bluetooth gamepads (BlueRetro)

- **`blueretro`**: the `libblueretro` submodule, BlueRetro's Bluetooth host, controller drivers and mapping as an ESP-IDF component (its README has the API). Its tasks run on core 0; its configuration and pairing keys are in the `storage` partition; its text goes to log frames under the tag `bt` (`oxctl log` sets the level). The Bluetooth name is `BlueRetro_Xbox_XXXX`.
- **`bt_xid`**: the output. The first controller to connect is the console's pad (BlueRetro gives each controller the output of its Bluetooth slot, which isn't always 0; when that controller goes, another connected one takes over): BlueRetro's generic state becomes the 18-byte XID state (`xid_pad_set`), the console's rumble goes back to the controller, and the pad is plugged into hub port 1 while a controller is connected and unplugged when it goes (`UsbDev::SetPadPresent`). Started at boot; the `Xbox` USB profile then starts with the pad absent until a controller connects.
- `oxctl bt status` (pairing, controllers connected, config page; command `0x0800`), `oxctl bt pair on|off` (`0x0801`), `oxctl bt forget` (`0x0803`: disconnects every controller and clears all pairing keys). Pairing runs at boot while no controller is known.
- BlueRetro's BLE configuration page (button mapping and its other settings, stored in `storage`) has no authentication, so it is closed at boot; `oxctl bt config on|off` (`0x0802`) opens it, advertised while no controller is connected. Its firmware update is disabled: OpenOX's firmware is updated through its own paths.
- Without standby, controllers reconnect each console power-on (~1–3 s). With standby (optional), they stay connected and can wake the console (needs the power-button wire).

## 11. NeoPixels, LCD

- **NeoPixels**: 2 RMT channels, WS2812/SK6812, length/brightness/current-limit in NVS. Status overlay priority: NOR write/flash-emu > error > console off > no LCLK > serving > idle; plus legacy LED renderer and per-player colours.
- **LCD**: SPI (ST7789/ILI9341 class) on `periph_bus` (shared with the SD card) with its own CS + DC + backlight PWM; LVGL. Shows console state, active ROM, controllers, COM activity; renders legacy LCD text; ROM picker driven by gamepad.

## 12. PC protocol (`host_link`)

UART0 through bridge channel A, 921600 baud 8N1 (higher if the bridge allows). Binary only; `tools/oxctl.py` is the human interface.

- **Framing**: COBS, frames delimited by `0x00`. Frame = `type (1) | seq (1) | len (2, LE) | payload | CRC-32 (4, LE)` before encoding. Anything that fails the CRC is dropped, so boot-ROM text before the app starts is ignored.
- **Flow**: the PC sends requests; every request gets exactly one response with the same `seq` (`OK` + payload, or `ERR` + code). The ESP32 sends unsolicited `EVENT` frames (console reset, bank swapped, SMBus alert…).
- **Logs**: once the app runs, ESP-IDF logging is redirected into `LOG` frames; nothing else is written to UART0.
- **Bulk data** (ROM images, bitstreams, firmware): `begin(target, size, crc32)`, then `data(offset, ≤ 4 KB)` chunks each acknowledged, then `end`, which verifies the CRC of the whole image before committing.

| Group | Commands |
|---|---|
| `sys` | version, status, reboot, ESP32 firmware update |
| `rom` | list, info, upload, delete, protect, select (`now` / `at_reset` / `default`) |
| `fpga` | info, bitstream update, recover, reset, boot config read/write |
| `nor` | the FPGA's flash, borrowed from the running FPGA (BIOS reads get 0xFF meanwhile): info, read, erase, program, CRC |
| `lpc` | serve on/off, D0 / LFRAME# mode, COM baud/route |
| `smbus` | raw read/write byte/word/block; named actions: reset, power cycle, power off, temperatures, tray/boot reason |
| `log` | level per tag |
| `prog` | one programmer protocol packet in, its reply out (07-console-protocol): the PC gets everything the console does |
| `usb`, `bt`, `led`, `legacy` | (later phases) |

## 13. SMBus (`smbus`)

The Xbox SMBus (LPC header pins 13/14, 3.3 V) is wired to the ESP32, not the FPGA: it is slow and protocol-level, with no hard timing.

- **Master** (I2C0, 100 kHz): reads the SMC (0x10) for tray state, fan and boot reason; the temperature sensor (0x4C) for CPU/board temperatures; the EEPROM (0x54) read-only. Writes SMC commands for reset, power cycle and power off, so `oxctl` plus the kernel debugger on COM make a complete remote debugging setup. The MCPX is the other master: transactions are short, start only after the bus has been idle, and lost arbitration is detected by the I2C hardware and retried. The master exists only for the length of one transfer and is torn down afterwards, so a failed transfer can never leave the console's bus held (which makes its boot fail).
- **Power on** is not possible over SMBus without standby power (the ESP32 is off with the console); it needs the optional standby supply and power-button wire.
- **Slave** (I2C1 on the same pins, address `0x60`): the default state, back after every master transfer. No clock stretching, so it never holds the bus. For now it only ACKs its address; later it exposes small data tables to Xbox-side software.

## 14. First firmware scope

1. `fpga_link`, `fpga_svc` (status, IRQ).
2. `cfg_bus`: program and verify the FPGA's NOR; recovery.
3. `host_link` + `oxctl`.
4. `rom_mgr`: upload, catalogue, selection, boot config.
5. `smbus` master.

USB, Bluetooth, legacy personalities, SD and LCD follow.
